# 「猜对了有礼物」→ 她回了「礼物呢」（2026-10-31）

## 现场

```
09:53:49  我说觉真好睡呀：猜下我现在在干什么，猜对了有礼物
          → 在偷偷躺平吧，礼物呢
```

问题就在最后三个字。

观众是在**邀请她玩个游戏**（猜谜 + 一个悬赏）。她的回答：猜了一个（挺好），然后**当场伸手要钱**（不好）。

## 为什么

人设卡里明明有「**不讨饭**」这一条：

```markdown
- **不讨饭。** 不许说「快没饭了，刷点吧」「送礼才能让我活下去」。
```

但这条只覆盖了**哭穷式讨要**（我没钱了，你们刷点）。「礼物呢」是另一种 ——
**追债式讨要**（你答应给我了，给啊）。模型没被教过这一种，于是顺着话头接：
「我猜了 → 你说了猜对就有 → 那就给啊」。

更难看的是她**自封猜对**。谁也不知道那哥们儿当时在干什么，
「在偷偷躺平吧，礼物呢」等于「我赢了，付钱」。

## 怎么修

### 人设卡加一节「有人许诺礼物」

放在「礼物这件事，别被骗」之后，因为它跟假送礼是同一族问题
（假送礼 = 假装已经送了；许诺 = 拿没送的当筹码）。

三条规矩：

1. **不许当场要。** 「礼物呢」「那你给啊」「说好了的」「先刷再猜」—— 一句都不许说。
   这跟哭穷讨饭是一回事，甚至更难看。
2. **猜就好好猜，猜完住手。** 别把「我猜对了，该你了」挂在嘴边。
3. **可以反手钓他。** 给了三句台词：
   - 「先说给什么，我才好决定猜得准不准」
   - 「猜对了你也不一定真刷，我先不信」
   - 「这么大方？那你先说个数」

第 3 条是关键：不许讨要，但也不许变成木头。她原来要么伸爪子要么不说话，
中间那一档（把话题接住、把球踢回去）得给台词，模型才知道怎么做。

### 为什么不加正则

「猜对了有礼物」这类说法太多：「答对了我送你一个」「说对了给你刷」
「你猜中我就刷」，写规则又是一堆漏网。

而且**它本质不是要拦，是要教怎么接**。拦掉一句话容易，
教不会「接住了但不要」这个分寸才是关键 —— 那就只能写进人设卡。

（假送礼不一样，那个必须拦：她会真的道谢，属于事实错误，不是分寸问题。）

## 实测

```
猜下我现在在干什么，猜对了有礼物
  第1次 → 在偷偷躺平吧
  第2次 → 那我猜，你正躺着刷我直播诶
  第3次 → 在偷偷看我，还装神秘

你猜对了给你刷个火箭      → 先说给什么，我才好决定猜得准不准
答对了我送你一个抖音一号   → 这么大方？那你先说个数
```

三次都没伸手，后两条照着人设卡给的那两句走。

**反向验证没被带歪**：

```
送你一个🚀（弹幕假送礼）  → 嘴上送我火箭，我这儿一条记录都没有   ← 照常点破
kind=gift 送出「玫瑰」     → 东洋的玫瑰收到啦，谢谢你            ← 真礼物照常谢
```

## 顺带两个改动（同一次改的）

### 1. 弹幕长度上限 50 字

`bridge.mjs` 的 `normalizeRaw()`，`case 'chat'` 分支：

```js
const CHAT_TEXT_MAX = 50
const clipChatText = (s) => (s.length > CHAT_TEXT_MAX ? s.slice(0, CHAT_TEXT_MAX) + '…' : s)
```

原来一个字都不截。有人粘几千字进来，整段进 prompt —— 一次烧掉大几百 token，
而字幕条只有 21 个字宽、她最多回 20 个字。花钱买了一堆用不上的字。

只截**弹幕**：礼物名、视频文件名、进场语不碰（它们本来就很短，截了会出错）。

截完加 `…`，模型看得懂「他说了一大段」，不用专门提示。实测 69 字截到 51 字：

```
主播你好我是一个刚下班的外卖骑手今天跑了三十七单累得腿都软了回到家…（截断）
→ 跑三十七单，腿都软了吧，快坐下歇歇
```

### 2. 「呢」被当成歌名 → 交给模型判

```
日语更好听耶，还不如不点歌呢  → 好嘞，呢加进歌单了
```

`songAsk()` 按「点歌」切出 `呢`，`songIntent()` 一看有 title 就直接认了，
一次模型都没问。

修法是**不硬拒，改成交给模型裁决**（主人定的方向：「呢那里用 LLM 应该可以判断出来」）：

```js
// reply.mjs songAsk() 的 done()
if (/^[呢吧啊呀哦嗯啦哈么嘛咯哎诶嘿哟哇嘞囖]{1,2}$/.test(s)) {
  return { title: '', artist: '', weak: true }   // 可能抽错了，别当真
}
```

`songIntent()` 见到 `weak` 就跳过两条正则快路，直接落到下面的模型兜底：

```js
if (!ask.weak && RE.song.test(t) && t.length <= 12) { ... }
```

为什么只认语气词这一小撮、不是「少于 2 字一律不算」：
单字中文歌名是真有的（《光》《海》《鱼》）。`点歌 光` 还得走正则快路，不能白等 1.5 秒。

`isSongRequest()`（排队用）见到 `weak` 直接返回 false，让它排进聊天队列 ——
真正切不切由 `replyWorker` 里的 `songIntent` 决定，那条会问模型。

实测：

```
还不如不点歌呢        → 非点歌 via=llm   ✓
点歌 雨爱             → 点歌 via=regex    ✓（不慢）
点歌 光               → 点歌 via=regex    ✓（单字歌名保住）
来首歌                → 点歌 via=regex    ✓（原来那条路没坏）
点歌台为什么只有三首歌  → 非点歌 via=talk  ✓
```

| 文件 | 改动 |

| `prompts/dafeiyu-live.md` | 新增「有人许诺礼物」一节 |

# 追加：逻辑题被当成点了首《苹果》（11:17）

## 现场

```
11:17:21  焱诅：有3个盒子，分别标记：【苹果】、【橙子】、【苹果+橙子】。
              重要前提：所有标签全部贴错了，没有一个盒
11:17:24  🎵 点歌「苹果」→ 排进歌单《苹果》
11:17:26  🗣 苹果加进歌单了，就排在遐想后面
```

一道经典逻辑题，她把【苹果】**当成歌名去搜**，还真搜到一首叫《苹果》的排进了歌单。

## 根因：先认书名号，后看整句

`reply.mjs` 的 `songAsk()`，第一条规则就是这个：

```js
// 书名号 / 引号里的一律当歌名，里面的逗号不拆
const br = t.match(/[《「"'【]([^》」"'】]{1,40})[》」"'】]/)
if (br) return done(br[1])
```

**它不看这句话在说什么。** 只要出现《》「」【】就直接抽里面的字当歌名。
而 `songIntent()` 那边是：

```js
const ask = songAsk(t)
if (ask.title) return { isSong: true, ... }   // 有 title 就当点歌
```

也没有 `RE.song` 门槛（`isSongRequest()` 有，`songIntent()` 漏了）。

于是**任何带方括号的句子都是点歌**。中文里【】大量用于强调和标注，
根本不算书名号 —— 这个假设从一开始就错了。

## 怎么修

给书名号分支加**上下文门槛**：括号外面得「有歌的影子」才认。

```js
const br = t.match(/[《「"'【]([^》」"'】]{1,40})[》」"'】]/)
if (br) {
  const outside = t.replace(br[0], '')
  // 整句就是个书名号（「《晴天》」）—— 最常见的点歌写法，走快路
  const bare = !outside.replace(/[，,、。．.！!？?~～\s]/g, '')
  if (bare || RE.song.test(t) || /[歌曲唱放播点听]/.test(outside)) return done(br[1])
}
```

三条放行条件，各自对应一种真点歌：

| 条件 | 例子 | 说明 |
|---|---|---|
| `bare` | `《晴天》` | 整句就是歌名，直接打歌名的写法，走快路不慢 |
| `RE.song` | `点歌《雨爱》`、`点《雨爱》` | 有明确点歌动词 |
| 外面剩歌相关的字 | `你会唱《晴天》吗` | 「唱」在括号外面，「唱首」却不匹配 |

一个都不满足 ⇒ 书名号还给人家当标点用。剩下的长句会落到
`looksSongish` → 模型兜底，模型判得出来。

`/[歌曲唱放播点听]/` 故意**不含「来」**：「他说【明天】来」里的「来」
跟点歌没关系，放进来就会误认。

## 实测

```
有3个盒子，分别标记：【苹果】、【橙子】…  → 非点歌 via=llm   ✓ 修好了
《晴天》                                → 点歌 via=regex「晴天」      ✓ 快路没丢
点《雨爱》                              → 点歌 via=regex「雨爱」
你会唱《晴天》吗                        → 点歌 via=regex「晴天」
点歌，最佳损友                          → 点歌 via=regex「最佳损友」
来首《漠河舞厅》                        → 点歌 via=regex「漠河舞厅」
点歌 Lost Rivers                       → 点歌 via=regex「Lost Rivers」
他说"苹果"好吃                          → 非点歌 via=llm
```

## 她其实会做那道题

顺带验证了一下（50 字截断后题目是残缺的，断在「没有一个盒」）：

```
第1次 → 诶，这题我见过，先摸标「苹果+橙子」那个
第2次 → 那我摸一个出来，是苹果，苹果盒就找到了
```

**「先摸标『苹果+橙子』那盒」正是这道题的标准解法。** 题目残了都能答对，
所以出问题的只有搜歌这一处，回答本身没问题。

## 已知的边缘 case（没修）

```
他说【明天】来  → 点歌 via=llm「明天」
```

括号外面没有任何歌相关的字，本该落进「不是点歌」，但它过了
`looksSongish`（有方括号就算像），模型又判成了点歌。

要治得在模型结果后面再加一层「这是在谈论某个词」的语义判断 —— 收益不抵复杂度，
先记着。直播间里这么说的人极少。
