# 2026-10-29 直播伴侣关播/开播通道逆向

目的：找到"能让 agent 程序化触发开播/关播"的位置，绕开鼠标模拟。

结论先行：**找到了完整的控制协议，但它在正式版里是死代码，未接线。软件层面无可用入口。唯一可靠方案是物理 HID。**

---

## 一、先说拦截层：为什么点不动

不是坐标问题，不是 DPI，也不是被用户抢占。是输入注入在系统层面被拦。

| 验证项 | 结果 |
| --- | --- |
| 进程窗口站 | `WinSta0` / `Default`（正常交互桌面，不是服务会话） |
| `SetCursorPos(2335,1832)` | 返回 **0（失败）**，且 `GetLastError()` = **0**（不给错误码 = 被 hook 后直接 return FALSE） |
| `SendInput` | 函数可绑定，但注入无效果 |
| windows-mcp `Click` | 返回"已点击"，实际光标纹丝不动（真实光标 `1014,737`，MCP 报 `2028,1474`） |
| `ControlStatus` | 全程 `state: ai`，排除用户抢占 |
| 沙盒外执行 | 结果一致 |

拦截者：`C:\Program Files (x86)\edrAgent\`（**抖音安全组件 5.3.3.53**），含 `edrservice.exe` / `secsdk.dll` / `gp.dll` / `sscronet.dll` / `parfait.dll`，走 named pipe 通信，上报 `https://seraph.zijieapi.com`（app_id 2079）。

它的职责就是**反自动化**。所以"用模拟点击操作直播伴侣"这条路，从设计上就是被堵死的。

> 注：`2026-10-29-MCP补充-Windows-MCP与REA.md` 里"让主进程 Trust 后重新派生就能点动"的猜想**不成立**——现在 windows-mcp 就是主进程正常加载的，输入照样被封。

## 二、逆向出的关播链路

安装位置：`D:\Apps\zhibo\webcast_mate\`，Electron，**JS 未加密未打包**（`resources/app/index.js` 2.7MB 明文）。

链路：

```
外部指令 → 命名管道 \\.\pipe\mate-autotest
         → ar.listen("endLive")   ← 日志会打「接收关播指令」
         → Bn()                    ← 真正的关播函数
         → ar.response("endLive")  ← 回执
```

指令表（`description` 是明文）：

| key | 含义 |
| --- | --- |
| `startLive` | 开播 |
| `endLive` | 关播 |
| `release` | 关闭直播伴侣 |
| `pk` / `login` / `logout` / `floatWindow` | PK、登录、悬浮窗 |

消息编码（`#socketWrite` 作分隔符的 JSON 流）：

```
发：#socketWrite{"key":"endLive","data":{...}}
收：#socketWrite{"key":"reps","data":{"key":"endLive"}}
```

**方向是反的**：外部程序当 server，直播伴侣当 client 连上来。

## 三、为什么这条通道用不了（死代码证据）

| 证据 | 说明 |
| --- | --- |
| 管道从未存在 | `Get-ChildItem \\.\pipe\` 里没有 `mate-autotest`（只有 `mate-ai-*`、`mate-mediasdk-pipe` 等） |
| server 类无 init 调用 | `new class extends rr { name:"server", init: ... listen("\\\\.\\pipe\\mate-autotest") }` 实例化后**没人调 init()** |
| 我们自己起 server 测试 | 管道可创建、可监听，但 25 秒内**无 client 连入** |
| client 不重连 | `listen()` 里 `waitConnectReady().then(...)` 只在注册时连一次，失败则永久放弃 |
| 初始化入口无人调用 | `Yn`（"初始化Executor"）在整个 bundle **零调用点**，`qn` 只被 `Yn` 调用 |

即：这套 test-controller / test-executor 是打包时保留、**运行时从未接线**的测试框架。正式版不提供外部控制口。

## 四、排除掉的其他路径

| 路径 | 排除理由 |
| --- | --- |
| `127.0.0.1:31133`（唯一 LISTENING） | 是 Express，但 `/api` `/health` `/status` `/resource` `/ping` 全部 404；来自 `@byted/pc-sdk-node` 的加密子服务（代码里有 `encrypted` / `siv` / "管道到期自动关闭"） |
| CDP 远程调试 | 无 `DevToolsActivePort` 文件，netstat 无监听端口 |
| `MATE_AI` IPC | 方法只有 `liveStarted` / `liveStopped` / `llmGenerate` / `setAsrPhrases` 等，是**内置 AI 助手**的通道，只能通知状态，不能反向控制 |
| `PostMessage` 投递点击 | Chromium 渲染进程丢弃外部合成鼠标消息；且实测该点已被微信窗口覆盖，脚本按校验自动放弃 |
| 渲染层 `END_LIVE` | 搜到的是 `END_LIVE_RANK_TYPE`（下播榜单类型枚举），不是关播动作 |
| 硬杀进程 | 异常断流，抖音会记非正常结束，不体面 |

## 五、结论与可行方案

**软件层面（模拟点击 / IPC / HTTP / 调试端口）在当前正式版上全部不可用。**

真正能让 agent "动鼠标"的方案只有一个：

### 物理 HID 点击器（推荐）

- 原理：Arduino Pro Micro / CH9329 模块，模拟 **USB 键鼠硬件**
- 为什么能成：`edrAgent` 防的是软件级 `SendInput`；USB HID 在系统看来就是**真鼠标**，无法与真人区分，也不触发任何 hook
- 成本：30~60 元
- 接入方式：串口发指令 → 硬件移动到关播按钮坐标 → 点击
- 配套脚本可由本项目提供（`tools/` 下），与现有控制台联动，实现真正的"点一下开播/关播"

### 不推荐

- 改 `index.js` 启用 test 通道：动第三方软件，升级即失效，且可能触发安全检测
- Frida 注入主进程调 `Bn()`：edr 反注入，**有封号风险**，不建议在账号直播期间尝试

## 七、补丁实测与完整性校验（16:40 ~ 16:55）

主人要求「修一下让它活」，于是直接改 JS 接线。**结论：技术上有效，但被完整性校验掐死，且无法分发给他人。**

### 7.1 补丁内容

只动 webpack 模块 `14180` 内部，两处：

| 位置 | 原 | 改 |
| --- | --- | --- |
| `registAutomate` 的守卫 | `if(n)`（n = isLocalTest） | `if(!0)` 强制启用 |
| 模块体末尾 | — | 追加 `setTimeout(()=>registAutomate(), 15000)` |

改完 `node --check` 两个版本均通过，13.1.1 与 13.2.3 代码完全一致。

### 7.2 关键证据：它连上了

用 `tools/mate-mcp.mjs` 先占住管道，再启动打补丁的直播伴侣，日志出现：

```
[mate-mcp] 已在 \\.\pipe\mate-autotest 等待连接
[mate-mcp] 直播伴侣已连接
[mate-mcp] 连接断开
```

**说明 `registAutomate()` 确实被触发、管道握手成功。** 但应用随即退出。

### 7.3 真正的拦路虎：integrityCheck

启动流程里在 `load_main_start` 之前有一步 `const b = await a`，失败就弹「检测到文件损坏」并 `app.quit()`。

判定逻辑：

```js
r = t[`files/check/0/${o}`], n = t[`files/check/0/${a}`]   // 从 systeminfo 响应取官方 hash 列表
const i = r.concat(n)
if (!oe(i, e)) { logger.error("corrupted files: ..."), {ok:false, failedList:i} }
```

**基准 hash 列表由服务器下发**，不是本地写死。

这意味着：
- 改任何被校验的文件，必然与原版 hash 不符 → 必被抓
- 想改校验函数本身？它就在被校验的文件里 → 死循环，无解

（我先前查 `checksum` / `asarIntegrity` 关键词得到 0，据此判断"没有完整性校验"，**这个判断是错的**。校验在 JS 逻辑层，用运行时算 hash 和服务端清单比对，关键词查不出来。）

### 7.4 附带事故：13.1.1 被更新干掉

补丁打到两个版本目录，重启时 launcher 顺势完成更新 13.1.1 → 13.2.3，**旧目录整个删除**，`launcher_config.json` 变为 `cur_path: 13.2.3`。

回滚时 `cp` 报源文件不存在才发现。以后打补丁前先看 `launcher_config.json` 的 `need_update`，别往即将被删的目录里写。

### 7.5 恢复步骤（已执行）

1. 用备份覆盖 `13.2.3/resources/app/index.js`（2720553 字节）
2. 备份文件移到 `.tmp/mate-backup/`，**不能留在应用目录**（防止被扫描）
3. 校验：补丁残留 0、`if(n)` 已恢复、`node --check` 通过
4. 用 `直播伴侣 Launcher.exe` 启动 → 12 进程正常

⚠️ 直接跑 `13.2.3/直播伴侣.exe` 会启动后自动退出（`Can not find startup.zip` 等初始化缺失），**必须走 Launcher**。

### 7.6 对「分发给别人」的结论

改文件方案**无法分发**：

- 基准 hash 服务器下发，每台机器、每个版本都会被独立校验
- 我们拿不到字节的签名私钥，改完必然对不上
- 客户端一升级，补丁立即失效且触发校验告警

剩下的运行时方案（Frida 注入 / 环境变量）不改文件、能过校验，但要面对 `edrAgent` 的反注入，且同样存在版本适配问题；把这类工具交给他人使用，还有违反平台协议与合规风险。**物理 HID 是唯一既无侵入、又能复制的路子。**
