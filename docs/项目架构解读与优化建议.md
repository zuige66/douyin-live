> 读了一遍核心代码（bridge.mjs / reply.mjs / native/render.py / native/overlay.py /
> settings.html / music.html / README / 已有优化方案）后整理。
> 目的：把"这个系统到底怎么拼起来的"讲清楚，再列出**还能**改什么。

---

## 一、一句话定位

这是一个**抖音直播伴侣用的虚拟主播叠加层**：一个 1920×1080 的"画面窗口" +
一套**自动回复/点歌/放素材**的弹幕桥 + 一个网页设置面板。
核心思路是**不用浏览器做画面**（Chromium 在这台机器上每 33 秒崩一次），改用一个
Python 进程 + 原生 Win32 窗口 + PIL 直接画位图，再用 ffmpeg 解码礼物视频。

---

## 二、整体架构（分层）

```
 抖音直播间（弹幕/礼物/进场/点赞）
        │  douyin-mcp（第三方 MCP，把抖音事件喂进来）
        ▼
 ┌─────────────────────────────────────────────────────────┐
 │  弹幕桥 bridge.mjs   ← 整个系统的中枢                      │
 │  · get_live_events 全量数组 → 自己维护游标做增量去重        │
 │  · classify/normalize 事件 → 聊天/礼物/进场/点赞/关注       │
 │  · 回复路由、音乐调度、媒体调度、用户记忆、诊断            │
 └───────┬──────────┬──────────┬──────────┬───────────────┘
         │state.json │ SSE      │ /media   │ 面板 API（/dy /user /persona /music /gift）
         ▼           ▼          ▼          ▼
   原生画面窗口    旧浏览器     音乐后端    设置页 / 音乐页
   overlay.py     overlay      （单身汉     settings.html
   +render.py     index.html   dsh-music   music.html
   +media.py      （历史遗留）  / QQ音乐）
        │              │           │
        ▼              ▼           ▼
   直播伴侣        直播伴侣      本机播放器
   "窗口捕捉"      "窗口捕捉"    (SMTC/WASAPI)
```

要点：**所有数据都从桥出**，画面窗口和旧浏览器只是两种"取数方式"；面板只是"改配置
的网页"，不碰 MCP。桥是唯一既读抖音、又管回复、又管音乐、又管素材的进程。

## 三、各模块详解

### 3.1 画面层：为什么不用浏览器，怎么做的

- **生产路径（当前在用）**：`native/overlay.py` 用 `ctypes` 直接调 Win32 建一个
  1920×1080 无边框窗口，`native/render.py` 用 **Pillow** 把整帧画成位图，
  经 DIB + `BitBlt` 贴上去（一次约 2ms）。
  - 静态层（`build_base`）只合成一次并缓存（主播牌/卡片/点歌台/标语），只在
    "歌名或队列变了"时重建。
  - 逐帧（`compose`）只画会变的东西：数字、字幕、皮套动作、右侧"电脑"里的素材。
  - 没有动作素材时**只在状态变了或秒数跳了才重画**，空闲 CPU≈0；有素材时把节拍
    提到 15fps。
  - 礼物素材走 `native/media.py`：桥只负责"放哪一份、放多久"，画面负责解码
    （ffmpeg / MCI），播完回报 `/media/done` 让桥顶下一首。
- **历史遗留（index.html）**：旧的浏览器叠加层，仍能被桥静态服务，但**已不用**。
  代码里还留了内存看门狗、遥测、轻量模式等，是踩过坑的遗迹。新机器上不要依赖它。

> 结论：现在"页面"这个词要分清——**给观众看的画面不是网页，是原生窗口**；
> 真正的网页只有设置页/音乐页（下面 3.4）。

### 3.2 弹幕桥（中枢，bridge.mjs）

- **数据入口**：`douyin-mcp` 的 `get_live_events` 返回"监听以来的全量累积数组"，
  **没有 id、不清空**。所以桥自己维护 `cursor` 做增量；任何 `start_live_listen`
  都会让上游把历史重吐一遍，因此换了房间必须 `cursor=null` 重建基线，且同样的
  房间+监听还活着就**不重听**（否则会回放旧弹幕）。
- **事件分类** `classify()`：靠字段形状反推类型（service 层把 `Kind` 丢了），
  支持 camel/snake 两种键名格式（抖音 reflow 两种都有）。
- **三条消费路径**：
  1. 原生窗口：每 0.4 秒轮询 `/state.json`（带 `x-dafeiyu-overlay` 头，桥据此判断
     画面是否真的在拉数据）。
  2. 旧浏览器：`/events` SSE 推（已弃用路径，保留兼容）。
  3. 回复引擎：弹幕进回复队列 → `reply.mjs` 出话 → TTS → 声音。
- **回复流水线**（`makeReply`）：广告入口闸门 → 本地优先判断（`betterLocal`）→
  路由（local/flash/dsh）→ 冷却判断 → 调模型 → 广告出口闸门 → 礼物必须点名校验。
- **礼物档位媒体**：文件名开头的数字决定档位（0=闲时/点播，1~4=礼物档），
  `giftMap` 把礼物名映射到档位；`flatGift` 可跳过礼物名做 1~4 混池。
- **用户记忆**：按抖音 uid 存 `cache/users.json`（到访次数、送礼、标签、备注、
  成长值），只存本机，面板可搜索/编辑/导出。
- **诊断**：`/healthz` 暴露回复档、冷却状态、上次失败原因、缓存命中账本、礼物通道
  健康度、画面多久没拉数据——"已回复 0"这种查不出来的问题靠它定位。
- **待机重试**：没房间/监听没起来时每 30 秒拿上次那坨东西再认一次房间。

### 3.3 话术引擎（reply.mjs）——设计得相当扎实

- **两档回复**：本地模板（零延迟、离线可用，按关键词分十来类） + 大模型
  （可选，失败自动退回本地）。
- **哪些走本地、哪些走模型**（`betterLocal`）：礼物、点歌、放视频、"你能做什么"、
  点赞一律本地（本地更准，且模型不知道队列/播放真实状态）；其余提问/闲聊/被夸走模型。
- **缓存前缀设计很聪明**：人设卡前 8 节（身份/铁律/对照表/底线…）三种性格共用，
  放 system 前缀；只有"性格尾巴"和"用户这一句 + 最近说过什么"放在 user 行。
  这样换性格或每条弹幕不同都不破坏前缀缓存命中（实测 84%~93%）。
- **广告双闸**：入口（弹幕含长数字串/联系方式/链接/广告话术直接拒）+ 出口
  （模型输出含这些也整句换掉）。只用"5 位以上连续数字"当信号，避免误伤正常句子。
- **冷却**：模型失败按 5s→15s→60s 递增，成功一次清零，避免网络抖一下就哑一分钟。
- **人设热重载**：`prompts/dafeiyu-live.md` + `cache/persona.json` 按 mtime 读，
  改完下一条生效；三种性格（毒嘴/女仆/有梗）切换不用重起桥。

### 3.4 页面（settings.html / music.html）：怎么做的

这两个才是真正的"网页"，由桥以**静态文件**方式服务（`serveFile`），被 DSH 插件
的设置页加载。

- **技术风格**：Material 3 Expressive 暗色，**纯色、零渐变、零阴影**（和画面层的
  M3E 紫保持统一）。CSS 变量定义一套色板，圆角卡片 + 胶囊按钮 + toast。
- **数据交互**：纯前端，`fetch` 桥的 JSON API（`/user/*` `/persona` `/music/*`
  `/dy/*` …），改完 `POST` 回去。面板不碰 MCP，所有"动抖音/动播放器"的事都经桥转发。
- **设置页三张卡**：用户记忆（搜/改/导出/清空）、人格性格（切性格、口头禅/禁用词/
  示例库、试说）、音源（网易云扫码、QQ 粘 Cookie、会员曲实测）。
- **音乐页**：连桥的 `/media`，轮询曲目 + SSE 收 `music` 事件，控制播放/暂停/切歌/
  音量。
- **已知坑（已记在记忆里）**：面板里永远用相对路径 `/api/...`；`/music/*` 前缀
  直到 2026-10-28 才挂到路由表里，之前扫码登录一直 404；`index.js`（宿主侧）的白名单
  不加新端点，面板请求就 404。

### 3.5 音源：四路独立、各管各的

| 音源 | 谁在放 | 怎么控制 | 备注 |
|---|---|---|---|
| **她说话 voice** | `tools/tts.py`（edge-tts）缓存命中即 0 延迟 | 回复出文本即念 | 说话时音乐压到 ~22% 再抬回 |
| **素材视频 media** | `native/media.py`（ffmpeg/MCI） | 桥决定放哪一份、放多久 | 右侧"电脑"屏幕里播，档位 0~4 |
| **点歌/背景乐 music** | **双源**：单身汉播放器 `dsh-music`（默认 `musicSrc='box'`，聚合网易云/QQ/酷狗）或本机 QQ 音乐（SMTC+WASAPI，`musicSrc='music'`） | 桥按"现在谁在放"分流 `boxCmd` / `mediaCmd` | 版权归零，VIP 曲要登录态 |
| **音效 sfx** | 礼物/关注/进场的短音效 | 触发式 | 优化方案里提过，未见落地代码 |

> 关键点：**"读得到"和"发得出去"是两条路**。读状态走 `/zhibo/music` → 桥 `/media`；
> 发命令走 `/media?cmd=`；而旧桥代码里 `?cmd=` 一律丢给 QQ 音乐链，点歌却在单身汉
> （`musicSrc==='box'`）→ 静默失败。单身汉的命令接口是 `POST /api/dsh-music/bridge/command`
> 且**排队执行**（回 `queued` 只是入队，要等轮询才真跑，生效 2~4 秒延迟）。

## 四、已经做得很好的地方（别动）

1. **原生窗口替代浏览器**：彻底解决了"渲染进程每 33 秒崩"的致命问题，空闲 CPU≈0。
2. **增量游标去重 + 同房间不重听**：绕开了 douyin-mcp 的全量累积数组陷阱。
3. **回复的前缀缓存设计**：把固定内容压进 system、变动内容放 user，命中率 84%~93%，
   既省钱又不破坏人设一致性。
4. **广告双闸 + 礼物点名校验**：直播安全相关的两条红线守得很死。
5. **冷却递增 + 诊断字段**：模型挂了不会哑一分钟，且 `/healthz` 能查为什么没回。
6. **人设/性格热重载、三性格共用记忆**：改人设不用重起桥，性格切换即时生效。

## 五、还能优化 / 改进的点（按性价比）

### P0 · 直接影响"像不像活人"

1. **长弹幕/长昵称溢出**（旧方案 P0-3，待办）：原生路径已默认关掉右侧弹幕列，
   但 `draw_danmaku` 里文字仍无 `fit_text` 截断。若以后重新开弹幕列，先套截断。
   `fit_text()` 已经写好，直接接上即可。
2. **字幕先出、再补声音**（旧方案 P0-1，已落地）：确认 `/say` 已是"先出字幕、
   声音合成好再补"；可再加**开播前预合成 30 句常用话**（"在呢/欢迎/好听"…），
   命中即 0 延迟——`tools/tts.py` 已有缓存，加个 `--warm` 词表即可。
3. **只回最新一条 + 同人 60 秒防复读**（旧方案 P0-2，已落地）：礼物仍 FIFO（稀罕、
   必须点名），聊天只留最新 + 5 秒间隔。

### P1 · 影响"跑一晚上会不会出事"

4. **`events.jsonl` 只涨不减**（旧方案 P1-2，待办）：现在 36KB/43 分钟，按天切、
   保留 7 天，避免长跑把盘吃满。
5. **房间没人也自言自语白烧 token**（旧方案 P1-3，待办）：`online > 0` 才开口，
   离线时只做动作不做语音。
6. **每帧重画整个 1920×1080**（旧方案 P1-6，待办）：`compose` 仍是全帧合成。
   可只重绘皮套那一块（600×700）+ 变化的小卡片，UI 层分块缓存，CPU 能从 ~34% 降到 ~20%。
   这是目前最大的常驻开销点。
7. **弹幕整块刷新像 PPT 翻页**（旧方案 P1-5，待办）：新的一条淡入 + 旧的往上推
   （当时针对浏览器路径；原生路径若恢复弹幕列要做）。
8. **两个渲染路径的视觉漂移风险**：`index.html`（浏览器）和 `render.py`（原生）
   是两套独立实现的版式，长期要各自维护、容易不同步。建议把 `index.html` 明确标为
   "仅调试/回退用"，并在 README 注明"生产以原生窗口为准"，避免以后有人改了浏览器版
   以为改了画面。

### P2 · 锦上添花 / 出效果

9. **点播动作**（比心/摇尾巴/摸摸头，`pet.py` 素材已有）：观众说"比心"→ 播对应动作帧，
   互动感最强，2 小时能上。
10. **礼物分级答谢**：大礼物（档位 3/4）→ 专属成功台词 + 更强反馈，直接拉动打赏转化。
11. **定时口播 / 整点报时 / 每 10 分钟引导关注**：留人。
12. **禁词房管**：骂人的不回、不念（直播安全），1 小时。
13. **观众记忆真正用起来**：现在记了 uid/到访/送礼，但回复里只在 `profileLine`
    带"老粉/榜一"这类，可考虑"点过歌的人下次直接叫名字"。
14. **音源双源收敛**：默认走单身汉 `box`，本机 QQ 音乐 SMTC 那条（`mediaCmd`）疑似
    遗留。若确认不再用，把 `musicSrc` 逻辑收敛掉，少一条分支少一处静默失败。
15. **数据面板**：在线/涨粉/礼物榜曲线，自己看直播效果用。

### 工程层面

16. **缺自动化测试**：除了 `bridge.mjs --selftest`（分类器 + 用户档案自检）和
    `overlay.py --selftest`（Win32 链路），回复引擎、媒体调度、音乐路由都没有单测。
    建议给 `reply.mjs` 的本地模板分支加一组快照测试（点歌/礼物/广告/梗覆盖）。
17. **设置页内联脚本语法风险**：`settings.html` 只有一段 `<script>`，一处语法错
    （比如 `try` 没 `catch`）会让整页按钮全废。改完用 `new Function(code)` 验一遍。
18. **配置漂移**：`llm.json` 含 API key，已注明别外传；`cache/` 里的 `users.json`
    `persona.json` `media.json` 都是运行时产出，`.gitignore` 要确认没收进去
    （已踩过 git 把 `cookies.txt` 暂存进去的坑）。
