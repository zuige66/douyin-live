# 音乐链路现状 + otter-music 评估（2026-10-28）

> 主人原话：「感觉现在放歌曲点歌切歌队列这条线还是有问题，现在是 qq 音源吗，
> https://github.com/DJChanahCJD/otter-music 看看这个可以吗，先记录下来这个项目」

这份只写**查到的实况**和**能不能用**，代码一行没动。

---

## 一、先回答「现在是 QQ 音源吗」——不是

播放器配了三个 provider，但**真正在放的是网易云**。

实测证据（21:36 直接读 `/media`）：

```
title   : 太阳与地球
artist  : 卢广仲
trackId : netease:2745752426     ← 网易云
src     : box
```

`C:\Users\lirui\.dsh\dsh-music-huazai\settings.json`：

```json
"enabledProviders": ["netease", "qq", "kugou"]
```

三个源的状态，一个能用一个半残：

| 源 | 登录态 | 能不能放 | 现状 |
|---|---|---|---|
| **netease** | SVIP cookie 有效 | ✅ 能放 VIP 完整音源 | **唯一主力** |
| **qq** | `uin=3865077183; p_uin=; p_skey=` | ❌ VIP 曲取不到流（`QQ_URL_EMPTY`） | 登录态是**残的**，等于没登 |
| **kugou** | — | ❌ `KUGOU_URL_UNAVAILABLE` | 只能搜，不能放 |

`bridge.mjs:2546` 的打分已经把这套现实写死了：

```js
if (t.provider === 'kugou') s -= 30   // 只能搜不能放
if (t.provider === 'qq')    s -= 20   // 已登录也取不到 VIP，让位网易云
else if (t.provider === 'netease') s += 12  // SVIP 能放正版，优先
```

**所以「切到 QQ 音源」这件事本身不是解法** —— 除非把 QQ 的 `p_skey` / `qm_keyst` 补全
（重新扫码登录），否则 QQ 上正版热门歌全是 VIP，一律只有 30 秒试听。

## 二、现在这条链路的真实结构

```
观众弹幕「点歌，歌名，歌手」
      ↓
bridge.mjs: 正则抠出歌名/歌手
      ↓
boxRequestSong()  ── 搜三家 → pickTrack() 打分挑一个
      ↓
POST /api/dsh-music/bridge/command
      ├─ queue_next {tracks, offset}   插到当前曲后面第 offset 位
      └─ queue_add  {tracks}           追加到队尾（queue_next 失败时兜底）
      ↓
DSH 内置「单身汉」网页播放器（dsh-music-huazai）真的去取流、解码、出声
      ↓
桥每 1.5 秒轮询 nowPlaying 回读 → 对账点歌台 / 画面歌名
      ↓
热榜垫歌（maybeHot）保证没人点歌时不死寂
```

关键约束（写在 `bridge.mjs:1826` 那段注释里，别再踩）：

- 播放器接口是**排队**的，回 `{ok:true,queued:true}` 只代表入队，
  **要等音乐页面下一次轮询才执行**，生效有 2–4 秒延迟。
- 每次下发命令后必须**回读 nowPlaying** 才算数，不能信返回值。
- `queue_next` 是我们给播放器打的补丁，没打补丁 / 没重启 DSH 时会退化成
  `queue_add`（点歌排到热榜后面 → 点歌台显示和实际播放对不上）。

## 三、这次实际查到的三个可疑点

### 1. 系统音量 7%（最像「没声音/声音小」的元凶）

```json
"watch": { "ok": false, "why": "系统音量 7% · 耳机 (花再 Zero Air Pro)", "fixes": 1 }
"sys":   { "dev": "耳机 (花再 Zero Air Pro)", "vol": 0.067, "mute": false }
```

`musicWatchdog()` 里 `sysBad` 只做两件事：`musicWatch.ok = false` + 写 `why`。
**它不会自动把系统音量拉回去**（`bridge.mjs:2333-2337`）。

也就是说：网页播放器音量 70% 一切正常、队列正常、自检却红着，
实际从耳机出来的声音只有 7% —— 观众听到的就是「几乎没声」。
而且输出设备是**蓝牙耳机**，不是音箱，需要确认这是不是直播要用的设备。

### 2. 命令还排着队

```json
"box": { "ok": true, "alive": true, "pending": 1 }
```

`pending: 1` = 有一条命令入了队还没被执行。这是播放器接口的固有延迟，
但**连点五首的时候会叠加**（21:31–21:33 那两分钟点了 5 首）。

### 3. ~~队列上限只有 5~~ ← **这条是错的，已更正**

初版把 `rules.maxQueue: 5` 当成了点歌队列的上限。**不是** ——
它管的是**画面上的素材视频队列**（`MEDIA.queue`），跟点歌毫无关系。
详见下面「四、四个队列别搞混」。

而且实测日志里 `队列满了` 和 `点歌排到 6 条满了` **各出现 0 次**，
两个上限都从没被撑爆过。所以「点了没反应」不是队列容量造成的，
得往别处找（取流失败 / 命令排队 / 系统音量）。

## 四、四个队列别搞混（重要）

系统里叫「队列」的东西有四个，上限、管的东西、满了的后果全不一样。
排查时认错一个就会得出完全相反的结论（初版就认错了）。

| 配置/常量 | 变量 | 上限 | 管什么 | 满了怎么办 |
|---|---|---|---|---|
| `rules.maxQueue` | `MEDIA.queue` | **5** | **画面素材视频**：礼物视频、0 档点播视频 | `✕ 队列满了，丢掉`（静默丢弃） |
| `ZY_QUEUE_MAX` | `boxQueue` | **20** | 点歌台显示的待播歌（播放器真队列的对账快照） | 只截断显示，不影响播放 |
| `SONG_QUEUE_MAX` | `songQueue` | **6** | **还没处理的点歌弹幕**（「点歌，xxx」这条消息本身） | `点歌排到 6 条满了，丢掉最早那条` |
| `ZY_HOT_KEEP` | — | **2** | 热榜垫歌的**下限**（不是上限） | 队列少于 2 首就补热榜 |

### `maxQueue` 到底管什么

`bridge.mjs:1384`：

```js
if (MEDIA.queue.length >= mediaCfg.rules.maxQueue) {
  mediaLog(`✕ ${tag} 队列满了（${mediaCfg.rules.maxQueue}），丢掉`, 'warn')
  return { how: '丢弃', why: '队列满' }
}
```

`MEDIA` 是**画面媒体**（`native/media.py` 解码的那套 mp4），不是音乐。
什么时候会走到这里：正在播一个素材视频、新来的视频**既没资格打断**、
`sameTier` 又不是 `merge`（当前配置是 `queue`）→ 只能排队，
排到第 5 个之后来的就被丢掉。

所以它影响的是「刷礼物没反应」，跟点歌一点关系都没有。
在设置页「电脑 → 档位参数」附近能调。

### 点歌真正可能卡住的三个地方（按概率）

1. **取流失败**（`QQ_URL_EMPTY` / `KUGOU_URL_UNAVAILABLE`）→ 退备选、退热榜
2. **命令排队**（`box.pending` 不归零，2–4 秒延迟，连点会叠加）
3. **`SONG_QUEUE_MAX = 6`** —— 点歌**弹幕**排到 6 条，再来就丢最早的

第 3 条才是「点了没反应」理论上最像的那个，但实测日志里 **0 次触发**。
所以真出问题，先查前两条。

## 五、`歌被顶了` 的真实原因（21:53 事故复盘，已修）

主人截图说「我怎么感觉我的歌曲被顶了」。**不是感觉，是真的丢了。**

### 事故时间线（生产日志原样）

```
21:47:19  点歌「反方向的钟 周杰伦」→ 排进歌单
21:48:28  点歌「DAMIDAMI」       → 排进歌单《DAMIDAMI(哈基米版)》
21:52:22  点歌「DAMIDAMI，Sihan」→ 排进歌单《DAMIDAMI》
21:53:15  点歌「我不难过」        → 排进歌单《我不难过》
21:53:34  点歌「玻璃」            → 排进歌单《玻璃》
          ♫ 《玻璃》还堆在命令队列里（1 条），浏览器还没取走
21:54:31  ♫ 玻璃 - Gareth.T          ← 播的第 1 首
21:57:38  ♫ DAMIDAMI - Sihan/三Z    ← 播的第 2 首
22:00:48  ♫ DAMIDAMI(哈基米版)      ← 播的第 3 首
```

- **《我不难过》排进去了，一次都没播过** —— 从点歌台彻底消失。
- 播放顺序 **玻璃 → Sihan → 哈基米版**，跟点单顺序**完全倒过来**。
- 《反方向的钟》到 22:00 还挂在队列里没轮到。

### 根因：歌名比对把两首不同的歌判成同一首

`boxQueueSettle()` 每 1.5 秒对一次账，用的是 `sameTitle()`：

```js
return x === y || x.includes(y) || y.includes(x)   // 双向包含
```

而 `normTitle()` 会把括号里的内容**整段删掉**：

```
《DAMIDAMI(哈基米版)》 → damidami
《DAMIDAMI》          → damidami      ← 撞了
```

于是播《哈基米版》时，从后往前找"正在播的那首在队里第几位"，
先撞上的是**后面那首《DAMIDAMI》**，把它和它前面的一律当成"已经放过"清掉 ——
但《DAMIDAMI》(Sihan) 其实还没播。队列账本因此少了一首，
下一首点歌的 `offset = waitingSongs.length` 就少算 1 → 插到别人前面。
一次次累积，就成了**完全倒序**，而没轮到的歌直接从点歌台消失。

### 验证（用真实队列跑新旧逻辑）

队列 `[反方向的钟, 哈基米版, DAMIDAMI(Sihan), 我不难过, 玻璃]`：

| 正在播 | 旧逻辑命中 | 结果 | 新逻辑命中 | 结果 |
|---|---|---|---|---|
| 哈基米版（第 2 位） | **第 3 位** ❌ | 剩 2 首，Sihan 那首被误删 | 第 2 位 ✅ | 剩 3 首，正确 |
| DAMIDAMI（第 3 位） | 第 3 位 ✅ | 剩 2 首 | 第 3 位 ✅ | 剩 2 首 |

### 修法

队列对账**不再比歌名，改比 trackId**（`netease:xxx` 这种，唯一且不受标题规范化影响）。
拿不到 id 的老数据才退回歌名，且要求**归一化后完全相等**，去掉 `includes`。

搜索打分那边（`pickTrack`）仍然用宽松的 `sameTitle()` —— 那是"找歌"，
需要容错；这里是"对账"，必须精确。**两件事分开，别互相牵连。**

## 六、otter-music 能不能用：不能直接接，但值得抄思路

**仓库**：https://github.com/DJChanahCJD/otter-music （水獭音乐）

### 它是什么

**React + TypeScript + Vite + Capacitor 的移动端 App / PWA**（安装包 2.5 MB），
不是服务端程序。功能本身很完整：10+ 音源聚合、跨源搜索、智能换源、
五级回退（本地下载 → 缓存 → 直连 → 代理 → 下一首）、歌单导入、歌词、车载蓝牙歌词。

### 为什么接不上

1. **它不提供 HTTP API，也没有 MCP**。README 全文没有对外接口说明，
   自建部署（Cloudflare Workers + KV）只对外提供同步/管理后端（`/admin` + `SYNC_KEY`）。
   我们的链路需要的是「能被 `POST /bridge/command` 调用的服务端」，它是给人手点的 App。
2. **它依赖的上游 API 曲库是残的** —— 这是致命的。实测
   `https://music-api.gdstudio.xyz/api.php`：

   | 源 | 结果 |
   |---|---|
   | netease | ✅ 可用 |
   | tencent / qq / kugou / kuwo | ❌ `Value of 'source' is not supported` |
   | migu / joox / bilibili | ❌ 503 Service Temporarily Unavailable |

   而且 netease 这个源**搜不到正版原唱**。搜「稻香」「稻香 周杰伦」，返回 8 条：

   ```
   稻香(深情版) - Lucky小爱
   稻香        - Lie
   《稻香》童声 - 卡罗尔
   稻香(治愈版) - 周杰伦./街道办GDC
   稻香        - Jay
   稻香(正式版) - 沈幼楚
   稻香        - 何兵兵
   ```

   **周杰伦原唱一条都没有。** 取流是能成功的（320k MP3 / 8.4MB），
   但放出来全是翻唱 —— 这正好是我们现在**已经在解决的问题**
   （`pickTrack` 里给「歌手命中」+60 分、给翻唱 -25 分那套逻辑）。
   换成它，等于把已经修好的「点周杰伦听到翻唱」重新踩一遍。

3. **它明确「严禁商业用途」**，且 README 的 License 章节为空（仓库根目录未见标准 LICENSE）。
   直播是商业场景，法律上不干净。

### 唯一值得抄的东西

它那个**失败回退链**的设计思路是对的，我们现在是「取流失败就退下一个候选」，
它可以再往下走一层：

```
取流失败 → 退下一个候选 → 还失败 → 查本地缓存 → 再失败 → 换源重搜 → 最后才「这首放不了」
```

现在的 `boxRequestSong` 里 `rest` 备选数组已经做了「依次再试」，
但**没有本地缓存层** —— 热门歌反复点（《耀斑》《意外》一晚上点好几次）
每次都要重新走一遍搜索+取流，既慢又容易在高峰期失败。
这一层是可以自己补的，不需要 otter-music。

### 结论

| 问题 | 答案 |
|---|---|
| 能直接接进直播链路吗 | **不能**，没有服务端接口 |
| 它的音源比我们现在强吗 | **更差**，正版原唱搜不到 |
| 值得抄什么 | 多级回退链、本地缓存层 |
| 建议 | **不引入**，记在案；真要提升点歌成功率，自己做「热门歌本地缓存」+「补全 QQ 登录态」 |

## 七、如果要继续修，优先级建议

**已修（2026-10-28 晚，commit `553d8ca`）：**
- ✅ 点歌队列改用 trackId 对账 → 「歌被顶了 / 顺序倒过来」（见第五节）
- ✅ 0 档点播可以随机（`/media/config` 原来把 0 档排除在外）
- ✅ 礼物可以放 0 档（giftMap 支持 0 + 混池并入 0 档 + 礼物 0 档不被说话压低）
- ✅ 设置页「音源」页加「歌单队列」

**还没做：**

1. **系统音量这条**（成本最低、收益最大）
   `sysBad` 时不只报红，直接把系统音量拉到安全值（比如 60%），或者至少在面板上
   给一个「一键拉满」的按钮。现在只是亮红灯，主人得自己去点。
   ⚠️ 另外要注意输出设备：出过「蓝牙耳机 7%」和「扬声器 14%」两种，
   得确认直播到底该用哪个。
2. **`rules.maxQueue`（素材视频队列）** —— 如果观众反馈「刷礼物没反应」才需要调，
   跟点歌无关。真调的话顺带把「静默丢弃」改成给观众一句话。
3. **补全 QQ 登录态**（`p_skey` / `qm_keyst`）—— 但要注意：即便补全，
   QQ 的 VIP 音源仍可能因权限拿不到，需要重新实测一遍再决定要不要把 -20 撤掉。
4. **热门歌本地缓存**：播放器取到的流（或我们下载的 mp3）落盘，
   同一首歌 24 小时内再点直接本地放，跳过搜索+取流。
5. **播放器掉线要能兜住**：21:54:04 那条
   `插件不在（播放器界面没开），音乐回落到本机 QQ 音乐` 说明 DSH 抖一下，
   点歌队列就跟着重置。现在没有任何机制把「正在排的队」接回去。
6. otter-music：**只记录，不引入**。
