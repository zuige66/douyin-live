# 问「有什么推荐的歌」，她得真报歌名（2026-10-30）

## 她原来的反应

主人：「问她有没有推荐的歌曲，她好像不会给我真的推荐，而是避开不回，有点蠢蠢的。」

实测原样：

```
观众：有什么推荐的歌吗
大肥鱼：老熟人了还问，来首你爱听的那种
```

```
观众：推荐两首歌
大肥鱼：我这人不太会推荐诶，你想听什么
```

一个歌名都没提，还把球踢回去。

## 为什么

不是她不会推荐，是**没人告诉她歌单里有什么**。

播放器的 `queue.list`（歌单）以前只有一处用到 —— `buildFacts()`，那玩意儿**只在冷场
（`kind === 'chitchat'`）时才拼**。正常聊天的时候，user 行里关于歌单是一片空白。

她手里明明有一整个歌单，模型看不见，于是只能说「你想听什么」—— 这跟「你猜」没区别。

## 怎么做

### 1. 不做语义判断（主人定的）

第一个方案是写正则切「这句是不是在问推荐」：

```
推荐|有什么歌|来点歌|想听|放一首|有歌单吗…
```

主人否了：「语义分割太麻烦了，这个 llm 也不会消耗很多 token。」

理由站得住：这类问法太多太散 ——「有啥好听的」「最近在听什么」「来两首」
「有没有那种安静的」—— 规则写一堆还漏，漏了就是当场装傻。

**直接把歌单塞进每条聊天，让模型自己看这句话要不要用。** 一次几十个 token，
比养一套正则便宜得多，也不会漏。

### 2. `buildReco()`（`bridge.mjs`）

```js
function buildReco(ctx) {
  if ((ctx?.kind || 'chat') !== 'chat') return null
  const now = music && music.found ? String(music.title || '') : ''
  const list = Array.isArray(queue.list) ? queue.list.filter(Boolean) : []
  const pool = list.filter((s) => String(s) !== now)
  if (!pool.length && !now) return null
  return { songs: pool.slice(0, 6), now }
}
```

三个约束：

| 约束 | 为什么 |
|---|---|
| 只对 `chat` 返回 | 礼物 / 欢迎 / 点赞 / 点歌 / 视频梗话都不需要歌单，别白花 token |
| 排掉当前正在放的这首 | 推荐「正放着的这首」没有意义 |
| 最多 6 首 | 歌单可能上百首，全塞进去既贵又乱 |

一个都没有时返回 `null`，`songsBlock` 会走「歌单是空的」那个分支。

### 3. `songsBlock()`（`reply.mjs`）

```js
function songsBlock(r) {
  if (!r) return ''
  const songs = Array.isArray(r.songs) ? r.songs.filter(Boolean).slice(0, 6) : []
  const now = String(r.now || '')
  if (!songs.length && !now) {
    return '\n（播放器这会儿没开，歌单是空的。他要是让你推荐歌，就说歌单空的，让他点一首。）'
  }
  const list = songs.length ? `歌单里还有：${songs.map((s) => `《${s}》`).join('')}。` : ''
  const playing = now ? `正在放《${now}》。` : ''
  return `\n（${playing}${list}如果他问推荐、问有什么歌好听、想听点什么，就**从这份歌单里挑一首**直接说出歌名，再问一句要不要点。别反问他想听什么。歌单里没有的歌别编。）`
}
```

三句关键的话，每句都是针对一个真实毛病：

- **「直接从这份歌单里挑一首，说出歌名」** —— 不给动作，模型就会继续打太极
- **「别反问他想听什么」** —— 她现在的头号毛病就是把问题丢回给观众
- **「歌单里没有的歌别编」** —— 推荐一首播放器根本没有的歌，观众点了放不出来，
  比不推荐更丢人

贴的是 **user 行**，不是 system —— system 一动，前缀缓存当场归零。

### 4. 人设卡补一条

`prompts/dafeiyu-live.md`「有人点歌」那节后面加了：

```markdown
- 有人问「有什么推荐的歌」：**从歌单里挑一首，直接说出歌名**，再问一句要不要点。
  千万别反问「你想听什么」—— 你自己手里就有歌单，别把问题丢回给他。
  歌单里没有的歌不许编，说不出名字的推荐等于没推荐。
```

人设卡是长效的（每条都在 system 里，缓存友好），`songsBlock` 是逐条贴的（漏不掉），
两层一起上。

## 实测

有歌单：

```
观众：有什么推荐的歌吗
大肥鱼：雨爱，这首我私心爱，点不点                （13 字）
```

歌单空：

```
观众：推荐首歌呗
大肥鱼：歌单还空着呢，你点一首呗
```

## 反向验证：不会每句都扯到歌

最大的风险是「歌单塞进每条，她是不是见谁都聊歌」。实测三句无关弹幕：

```
今天好累啊    → 辛苦啦，先歇会儿诶
你叫什么名字  → 我叫大肥鱼，红鱼也行诶
红烧肥鱼      → 红烧鱼也行，反正都是圆滚滚的
```

一句都没提歌。指令里写的是「**如果他问推荐**」，模型分得清。

缓存命中 **93.2%**，跟改之前一样 —— 因为动的是 user 行。

## 为什么不塞进 system

`system` 是前缀缓存的对象。歌单一进 system，播放器每切一首歌缓存前缀就变一次，
命中率当场归零，一句成本涨十倍不止。

而且歌单本来就是「这一句的事」，不是「人设」，放 user 行本来也对。
