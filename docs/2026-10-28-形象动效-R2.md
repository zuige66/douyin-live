# 2026-10-28 形象动效改造（R2：AI 图生视频 → 透明序列帧）

## 为什么走这条路

zuige 给了一张广东工业大学拟人化立绘（1254×1254 白底 JPG），要求"按这个重新生成动态，要尾巴摇动"。

原方案有三个候选，最后选 R2：

| 方案 | 做法 | 为什么没选 / 选了 |
|---|---|---|
| R1 程序化微动 | 分层切图 + 仿射变换 | 动作幅度太小，尾巴摆动做不出来 |
| **R2 AI 图生视频** | 立绘 → 视频 → 抠像 → 序列帧 | **选它**，尾巴能真实摆动，画质上限高 |
| R3 Live2D | 分层绑定 | 2–3 天工作量，需要重画分层素材 |

同时否掉的还有两个错误方向：

- **GIF**：256 色调色板会毁掉红发渐变；只有 1-bit alpha，发丝和荷叶边必然白边；解码比 WebP 慢、体积大 2–4 倍。唯一优势是通用兼容，但我们走 Python + GDI 自绘，用不上。
- **角色交给 OBS 播**：README 已记录抖音禁止第三方 RTMP，OBS 只能经虚拟摄像头送进直播伴侣，多一道编解码，画质只会更差。

## 关键参数（改之前先读这段）

抠像的判据不是"亮度够白"，而是 **"够白 + 中性无色偏"**：

```python
cand = (mn >= 236) & (sat <= 8)     # mn = min(R,G,B), sat = max-min
```

理由是实测出来的：背景恒为 (251,251,251)，**sat = 0**；而角色身上的白都带色偏——围裙 sat=12、裙摆荷叶边 sat=17、白袜 sat=4。只按亮度分，围裙和荷叶边会被一起抠掉。

参数扫描结果（`tune.py` 产出 `probe/tune.png`）：

| 参数 | 结果 |
|---|---|
| `mn>=240, sat<=2` | 轮廓外残留大片白色碎块（背景浅灰纹理没被填充） |
| `mn>=238, sat<=5` | 碎块减少，仍有残留 |
| **`mn>=236, sat<=8`** | **碎块消失，荷叶边完好 ← 选它** |
| `mn>=234, sat<=12` | 干净，但荷叶边开始出锯齿 |
| `mn>=232, sat<=16` | 荷叶边下沿被啃出缺口 |

## 踩过的四个坑（都花了时间，别重犯）

### 1. `Image.fromarray` 出来的图是 read-only，`floodfill` 静默失败

```python
m = Image.fromarray(arr, "L")
ImageDraw.floodfill(m, (0,0), 0, thresh=0)
# → 一个像素都没填，且不报错
```

floodfill 内部的 `pixel[x,y] = value` 在只读图上抛 `ValueError`，被它自己的 `except (ValueError, IndexError)` 吞掉，直接 return。

**解法**：`Image.frombytes("L", (w,h), arr.tobytes())` 拿一份可写副本。

副作用：即便可写，`np.asarray(m)` 在 `fromarray` 之后也可能读回**修改前**的数据（`_arr` 缓存）。必须用 `np.frombuffer(m.tobytes(), ...)` 重新导出。

### 2. `thresh=0` 配灰度图，泛洪一出门就被截断

背景不是纯 251，有 250±3 的压缩噪声。种子值 251，邻居 248，`diff=3 > 0` → 传播立刻终止。

**解法**：二值化候选图 + `thresh=0`（二值图只有 0/255，不需要容差）；或者在灰度图上传 `thresh=30` 左右。本项目用前者。

### 3. 边缘带里算软 alpha，把背景涂成了半透明

第一版用「膨胀 − 腐蚀」取 2px 边缘带，带内按亮度算软 alpha：

```python
band = (dil > 0) & (ero == 0)
a = np.where(band, soft, hard/255)   # ← 错
```

带内原本是背景的像素也被赋了 0.2–0.6，叠在深色直播底上就是**轮廓外一圈虫蚀状灰白碎块**。

**解法**：直接从硬 mask 羽化，过渡只发生在真实边界。

```python
hard_img.filter(MinFilter(3)).filter(GaussianBlur(0.7))
```

### 4. 荷叶边和背景同为白色，物理上分不开

AI 视频里荷叶边下沿（纯白）和白背景在 yuv420p 压缩后混在一起，任何颜色判据都切不开，表现为裙摆下沿的竖向细缝。

**解法**：3px 闭运算（先膨胀后腐蚀）补齐 <3px 的缝，肉眼无感。

### 5. 🔴 泛洪灌进角色内部，把白色高光啃成黑点（最严重的一个）

第一版导出后，mp4 里角色身上布满密密麻麻的黑点：围裙、荷叶边的蕾丝、头饰、头发高光全是雪花状噪点。放大看就是 **alpha 被咬穿的小洞**——叠在深色直播底上变黑。

根因：角色的纯白高光和背景同为白色（sat 都在 8 以内

），而围裙的白色蕾丝**直接与白背景相接、没有深色描边**。泛洪从背景一路顺着蕾丝灌进角色内部，把沿途所有 `mn>=236 & sat<=8` 的高光像素全填成背景。

这不是调参能解决的——把 cand 收紧会残留背景白块，放松会啃边，两头堵。

**解法**：给角色本体加「填洞」保护，泛洪不得进入被强前景围住的封闭区域。

```python
strong = (mn < 215) | (sat > 22)        # 深色/彩色 = 确定的前景
# 填掉 strong 内部的洞 → 角色本体（含纯白高光、围裙、蕾丝）
bg = bg & ~solid_mask
```

效果：围裙区域 `alpha<40` 占比 2.77% → **0.00%**，全片封闭洞平均 **0.027%**（最严重一帧 755px，是发丝间自然空隙）。文件体积顺带从 17MB 降到 9.6MB，画面连贯后压缩率更高。

排查方法记一下：不要用 RGB 判断洞（透明背景的 RGB 是 0，会被误当成深色前景）。直接测 alpha —— 对 `alpha>200` 的 mask 填洞，剩下的 `out==0 & alpha<40` 才是真洞。

## 循环怎么处理

原视频首尾帧平均差 47.5（35% 像素差 >25），**不闭合**，直接循环会看到跳变。

方案：**pingpong**（正放 + 倒放），天然无缝，零重影。代价是周期翻倍到 10.2 秒 / 246 帧。

> 交叉淡化被否掉：尾巴是高对比形状，首尾混合会出现两个尾巴的重影。

## 第二轮：边缘白边与"马赛克闪烁"

第一版交付后反馈「尾巴和头发有马赛克闪烁」。排查下来是**三个独立问题叠在一起**，逐个定位：

### A. 缩放时白背景混进边缘（主因）

`PIL.Image.resize` 对 RGBA 是**四个通道独立插值**，完全不管 alpha。抠像后透明区域的 RGB 还留着原图的白（255,255,255），768→714 只缩 7%，LANCZOS 就把这些白色混进了轮廓，边缘全是 1–2px 白边。

验证方法：直接比对抠像输出（PNG）和成品，抠像输出的真白边只有 **6 个像素**，说明问题不在抠像，在缩放。

**解法**：预乘 alpha 之后再缩放，透明区 RGB 贡献为 0。

```python
pre = rgb * (a/255)          # 预乘
pre_r = pre.resize(size)
a_r   = a.resize(size)
rgb   = pre_r / a_r          # 反预乘
```

同时把插值核从 LANCZOS 换成 **BOX**（面积平均）。714 是缩小，LANCZOS 会在边缘振铃过冲，把颜色推亮一圈。

### B. 边缘 RGB 本身偏亮

轮廓最外 2px 的像素是「角色色 + 白背景」的混合，`unpremultiply` 在低 alpha 处会把误差放大，结果是偏亮的粉红，深色底上看着就是白边。

**解法**：`bleed.py` 的颜色扩散起点不用 `a>240`，而是**把前景腐蚀 2px 之后再取**，让轮廓最外 2px 的颜色完全由内圈重染。

```python
core = MinFilter(5)(a > 240)   # 向内收 2px
# 从 core 向外扩散 12px，覆盖整条边缘带
```

### C. alpha 边缘单帧抖动

相邻帧的边缘判定有 1–2px 随机性，播放时轮廓像在"呼吸"。

**解法**：`temporal.py` 对 alpha 做 **3 帧时域中值**（不是平均——平均会把尾巴的位置叠成半透明拖影）。实测每帧平均改动 648 个边缘像素，说明抖动确实存在。

24fps 下 3 帧 = 125ms，idle 的位移本来就 <2px，肉眼看不出代价。

### D. 预览编码放大了问题（容易误判）

第一版预览 mp4 用 560 宽 + `crf 20` + `yuv420p`，等于把 714 素材又缩了一次、还做了 4:2:0 色度子采样。细密的红发和高对比尾巴在这种编码下必然出块。

**规范**：预览一律用 `crf 12 + yuv444p`、不缩放。判断素材质量必须看 1:1，不能用缩略图——这条是第一次交付踩的坑，用 200px 缩略图验收漏掉了黑点。

## 现在还剩什么

4 倍放大看，边缘仍有轻微的亮红描边。这是**白底抠像的物理极限**：边缘像素本来就是「角色色 + 白」的混合，α 和前景色两个未知数只有一个方程。

1:1 显示尺寸（713×714）下肉眼不可见。要让它在放大 4 倍时也干净，只能：
- 换 1080p 源重新生成（提高边缘的绝对像素数），仍然无法根治
- 或者改用**分层素材 + 程序化动画**（R1 路线），从源头避免白底抠像

## 扩展动作段（第二轮生成）

idle 跑通后按需求追加动作。每段都是一次独立的图生视频（约 50–100 credits），
不能从一段里拆出多个动作。

| clip | 动作设计 | 状态 |
|---|---|---|
| idle | 呼吸 + 尾巴慢摆 + 眨眼 | ✅ 124 帧 12.0MB |
| happy | 上下雀跃 + 大笑 + 尾巴快摆 | ✅ 124 帧 11.9MB |
| sad | 低头下沉 + 闭眼下弯 + 尾巴下垂 | ✅ 124 帧 11.9MB |
| thinking | 歪头 + 眼神上飘 + 眨眼 | ✅ 124 帧 12.3MB |
| waiting | 左右张望 | ⏸ 未生成 |

### prompt 设计上的两条经验

1. **不要写手部动作**。thinking 最初想写「手托下巴」，改了——AI 重画手几乎必崩，
   改成「歪头 + 眼神上飘」，效果反而稳。
2. **显式写「Keep both hands exactly where they are, do not move or redraw the arms」**，
   能明显减少手部漂移。

### 各段必须共用同一裁切框

每段独立算 bbox 会得到不同的 crop 和缩放比，切换动作时角色大小会跳。
`pipeline.py` 从 `assets/pet2/manifest.json` 读 idle 定下来的 `crop=(6,0,768,763)`
和 `size=(713,714)`，所有 clip 强制用同一套。

实测四段的 bbox 本来就很接近（宽 750–756，差 <1%），所以不需要逐帧尺度归一化——
之前看缩略图以为 sad 变小了，量下来是误判。

### 统一管线

`pipeline.py` 把六步串起来，加新动作只要把 mp4 放进 `clips/<name>/` 然后：

```bash
python .tmp/r2gen/pipeline.py <name>
```

抽帧 → 抠像（含填洞保护）→ 去碎屑 → 颜色扩散 → 时域中值 → 导出。

## 情绪策略与接入（2026-10-28 定）

主人给的规则：

| 场景 | 播哪段 |
|---|---|
| 直播间没人 / 长时间没人说话 | `sad` |

### 实现：给 bridge.mjs 加一层「基线情绪」

原来的 `currentMood()` 只有「临时情绪 + 超时回 idle」，安静时永远 idle。
R2 的 idle 是闭眼微笑的，一直播看着像睡着了。所以要分两层：

```
临时情绪（礼物/被骂，带 until）  ←  优先级高，超时后交回基线
        ↓ 到期
基线情绪 baselineMood()          ←  由「在不在说话 / 有没有人 / 安静多久」决定
```

```js
function baselineMood() {
  const now = Date.now()
  if (now < speakUntil) return 'thinking'           // TTS 正在出声：睁眼
  if (stat.online <= 0) return 'sad'                // 房间没人
  if (now - quietSince > QUIET_FOR_SAD) return 'sad'// 有人但安静超时
  return Math.floor(now / MOOD_ALT_MS) % 3 === 0 ? 'thinking' : 'idle'
}
```

可调参数（环境变量）：

| 变量 | 默认 | 含义 |
|---|---|---|
| `ZY_MOOD_ALT_MS` | 20000 | idle/thinking 每 20 秒换一次，thinking 占 1/3 时间片 |
| `ZY_QUIET_SAD` | 60000 | 有人在线但安静 60 秒 → 切 sad |

同时：

- `MOOD_MS.happy` / `sad` 从 4.2s / 5.2s 改成 **10330ms**——一轮 pingpong 的时长，
  中途切走会看到动作戛然而止。
- 删掉安静时随机打哈欠/伸懒腰的逻辑（R2 没这两段，设了也会兜底回 idle）。

### pet.py 的映射按素材目录分两套

### 两个坑

**1. manifest 的 `loop_mode` 必须在顶层。** `pet._frame_index()` 读的是
`manifest().get("loop_mode")`，我中途按「每段一份」的结构写进 clips 里，
结果 pingpong 静默失效、退回直循环——首尾帧差 47.5，会看到跳变。

**2. 缓存和帧率必须一起调。** 原来的配置是 12fps + 缓存 24 帧：

| 配置 | 每帧耗时 | 24fps 占用 |
|---|---|---|
| 旧（缓存 24，10fps） | 30.3 ms | 73%（跑不动） |
| 缓存 160（装下一整段）+ FPS 24 | **9.7 ms** | **23%** |

124 帧一轮，缓存 24 等于没有缓存，命中率不到 20%。放到 160 后第一轮自然填满
（40ms/帧，刚好卡在 41.7ms 预算内），之后只查字典。内存约 144MB。

另外 `overlay.py` 的 `TICK_MS` 下限原来写死 50ms，等于把 24fps 强行砍成 20fps，
改成 33ms。
