# 画面编辑器（2026-10-28）

> 一句话：`editor.html` 拖一拖 → `POST /layout` → 桥写 `cache/layout.json`
> → `native/render.py` 发现文件变了，重建静态层。**1 秒内画面就变，不用重启、不用重开窗口。**

## 为什么是这条路

画面是 Pillow 逐像素画的（`native/render.py`），不是网页。编辑器里的坐标传不进
Python 的常量，所以两边必须有一份**合同文件**。选的是「只把数字外置」：

- `render.py` 的绘制逻辑一行没改，只是 `CARD_X / MON_Y / SUB_X` 这些常量
  改成由 `apply_layout()` 从 JSON 里写回。
- 读不到 / 读坏了 → 用内置默认版式。**任何情况下不会黑屏。**

被否掉的两条路：

| 方案 | 为什么不做 |
|---|---|
| 编辑器只做「假预览」，人工抄坐标 | 用两次就没人愿意抄了 |
| 整个画面换成浏览器渲染 | 已实测：Chromium 在这台机器上 33 秒 abort 一次，当初就是因此换的 Pillow |

## 文件

| 文件 | 干什么 |
|---|---|
| `editor.html` | 编辑器本体。桥的兜底静态路由直接发，`http://127.0.0.1:18081/editor.html` |
| `cache/layout.json` | 版式合同。编辑器写，`render.py` 读。**不进 git**（`cache/` 已被忽略） |
| `native/render.py` | 新增 `layout() / apply_layout() / comp_h() / _PALETTE`，其余照旧 |
| `bridge.mjs` | 新增 `GET/POST /layout`、`GET/POST /layout/bg`、`sanitizeLayout()`、`readRaw()` |
| `assets/bg.png` | 主人给的新背景（1920×1080） |

## layout.json 格式

```json
{
  "version": 1,
  "theme": "light",
  "bg": { "type": "image", "image": "assets/bg.png", "color": "#1E182A", "dim": 0.0 },
  "items": {
    "stats":     { "x": 64,   "y": 54,  "w": 452, "visible": true },
    "songs":     { "x": 64,   "y": 294, "w": 452, "visible": true },
    "banner":    { "x": 700,  "y": 26,  "w": 520, "visible": true, "size": 50, "align": "center" },
    "character": { "x": 675,  "y": 343, "w": 570, "visible": true },
    "monitor":   { "x": 1262, "y": 485, "w": 594, "visible": true },
    "danmaku":   { "x": 1386, "y": 180, "w": 470, "visible": false },
    "subtitle":  { "x": 510,  "y": 960, "w": 900, "visible": true }
  }
}
```

- **只有 `x / y / w`**。高度一律算出来（`comp_h()`），因为卡片高度是倒推的
  （点歌台 = 正在播放 + 3 首 + 提示两行），放开高度就会出现「拖矮了文字叠成一团」。
- `x/y` 是**左上角**，1920×1080 坐标系。
- `theme`：`dark`（紫，原版）/ `light`（白，配浅色底图）。
- `bg.type`：`image` / `color`。`dim` 是压暗 0–0.9。
- `danmaku.visible` 和 `monitor.visible` **二选一** —— 它俩抢右栏同一个位置，
  点亮弹幕，显示器就不画了（`ZY_DANMAKU=1` 也还能强制开弹幕）。

## 高度公式（两边必须一致）

| 组件 | 高度 | 备注 |
|---|---|---|
| stats | 216 | 32 + 36 + 3×46 + 10 |
| songs | 478 | 32+36+114+3×58+78+44（有歌手时） |
| banner | 64 | |
| character | `w × 1078/1005` | 皮套原图比例 |
| monitor | `w × 389/594` | 屏幕+边框+脖子+底座整体等比 |
| danmaku | `874 − y` | 自底向上排，拖 y = 改能显示几条 |
| subtitle | 86 | |

`render.py: comp_h()` ↔ `editor.html: H_()`，**改一个必须改另一个**，否则编辑器里
看到的框和真画面差一截，拖出来的坐标就是错的。

## 保存链路

```
editor.html  ──POST /layout──▶  bridge.mjs  ──原子写──▶  cache/layout.json
                                                          │ (mtime 变了)
                                    native/render.py  ◀───┘ base_key() 里带 _LAYOUT_STAMP
                                          └─▶ 重建静态层（~100ms）→ 下一帧就变
```

- 桥用 `写 .tmp → rename`，因为 `render.py` 每 0.5 秒 stat 一次；写一半被读到会解析失败。
  虽然会退回上一份（不黑屏），但下一次 mtime 变化才重试，中间那段时间表现为「拖了没反应」。
- `render.py` 里 `layout()` 有 0.5 秒限流，逐帧调用只多一次 `os.path.getmtime`。
  实测：34.4 → 35.4 ms/帧（噪声级）。

## 背景

- 下拉列表来自 `GET /layout/bg`（扫 `assets/` 里的 png/jpg/webp）。
- 「上传一张新图」= `POST /layout/bg?name=xxx.png`，请求体就是图片二进制，
  直接落进 `assets/`，上限 12MB。
- 路径会去掉 `..` 和前导斜杠，防止手填一个绝对路径读到别处。

## 加新组件（给 agent 的流程）

1. `native/render.py`：写一个 `draw_xxx()`，坐标从 `apply_layout()` 新加的
   `XXX_X/XXX_Y/XXX_W` 全局读，缺省值写死成「现在就好看」的那套。
2. `render.py: _layout_default()` 加一项；`comp_h()` 加一行高度公式。
3. `bridge.mjs: LAYOUT_KEYS` 加上键名（不加会被 `sanitizeLayout` 丢掉）。
4. `editor.html`：`COMPS` 加一行、`H_()` 加一行、`htmlOf()` 加一个 case。
5. `python native/render.py --shot out.png` 出图看效果。

## 已知限制

- **改 `render.py` / `bridge.mjs` 必须重启**：宿主那半边是插件加载时进内存的；
  画面进程也是长跑进程。只改 `editor.html` 和 `cache/layout.json` 不用重启。
- **改显示器宽度会让解码器重起**（`overlay.py` 每帧读 `render.SCR_W`），
  大约卡半秒。直播中尽量别动。
- 卡片里的**文字内容是写死的**（「刷礼物有惊喜」「点歌格式…」），编辑器改不了。
  改文案要动 `render.py`。
- 编辑器只能改现有 7 个组件，**不能新增**（新增等于要写绘制函数，见上面流程）。
- 编辑器里的预览是 HTML 近似：皮套用的是静态立绘，真画面是 `pet` 的动作帧。
