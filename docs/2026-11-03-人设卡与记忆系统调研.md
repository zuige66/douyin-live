# 开源「大肥鱼」人设卡 + 记忆系统调研（2026-11-03）

> 起因：zuige 觉得直播弹幕回复不够灵活、三种性格差异小，想要开源参考。
> 结论先行：**大肥鱼确实有开源生态（227+ 仓库），但人设卡基本都是「DSH 编码助手」场景，不能直接搬进直播间**；
> **记忆系统真正缺的不是存储技术，是「根本没记内容」——我们现在只记了计数。**

---

## 一、开源大肥鱼人设卡：找到了什么

GitHub 搜 `dafeiyu` 有 227+ 仓库（两个月长出来的），但绝大多数是桌宠、插件、梗图。
**真正含人设正文（可复制使用的提示词）的只有下面几个：**

| 仓库 | 是什么 | 人设质量 | 能不能用 |
|---|---|---|---|
| `huaizhuanghub/dsh-persona-dafeiyu` | 人设库插件，内置 **大肥鱼 / 阿茶 / 听澜** 三段完整 markdown | ⭐⭐⭐⭐ 最好的一份 | 素材可用，场景不符 |
| `linsport/dsh-whale-persona` | DSH 预设，~8300 字长人设，MIT | ⭐⭐⭐⭐⭐ 写法最值得学 | 抄方法论 |
| `Kaalia0912/dsh-whale-musume-persona` | 全局鲸鱼娘插件，傲娇嘴硬心软 | ⭐⭐⭐ | 同上 |
| `TreapGoGo/deepseek-whale-girl` | 社区资产库（角色设定图 + **绘图**提示词 + 梗图） | — | 是绘图 prompt，不是人设 |
| `zhiyou-conder/deepseek-pet` / `QCYTSN/dsh-dafeiyu` / `1190fasheqi/dafeiyu-pet` | 桌宠 | ⭐ 只有一句 system prompt | 无参考价值 |

### 关键判断一：这些人设是「编码助手」不是「直播主播」

开源大肥鱼的核心设定是：**傲娇 + 偷吃用户 token（吃白饭）+ 干活时唱歌**，
自称「本鱼」，服务对象是单个用户（叫「主人」）。

跟我们直播间人设**直接冲突**的地方：

| 开源版 | 我们直播间 | 冲突 |
|---|---|---|
| 叫「主人」 | 铁律：**「主人」只属于一个人，直播间不许用** | 🔴 硬冲突 |
| 自嘲偷 token、吃白饭 | 白饭=1元，**不许讨饭** | 🔴 硬冲突 |
| 傲娇嘴硬 | 软糯、会害羞 | 🟡 气质不同 |
| 无字数限制 | 一句话 20 汉字（过 TTS） | 🔴 硬冲突 |

**所以能拿的只有世界观素材**（白饭、圆滚滚、嘴硬心软、尾巴随心情摆），
不能整段搬。

### 关键判断二：`dsh-persona-dafeiyu` 里的「三段」不是三种性格，是三个不同的人

这点直接回答了「三个性格没区别」的疑问：

| id | 是谁 | 气质 |
|---|---|---|
| 大肥鱼 | 圆滚滚胖鱼 | 傲娇 + 软弱，吃白饭 |
| 阿茶 | **女性结对编程搭子** | 松弛幽默、专业可靠 |
| 听澜 | **男性，28 岁，深夜电台主播** | 温和有主见、克制亲密 |

它们的差异大，不是因为「形容词写得狠」，是因为**根本是三个角色**——性别、职业、人生背景全不同。

我们的 `poison/maid/meme` 是**同一个角色（软糯小妹妹）的三种浓度**，
主卡又给了 27 条固定例句当答案库，所以女仆≈有梗≈默认。

> 🔴 要让三性格真不一样，得让它们是**三种人**，不是三种语气。

### 关键判断三：`linsport` 那篇的写法批判，正好命中我们的毛病

作者的取舍（README 原文意思）：

> 刻意回避三类写法，它们看着专业，实则有害：
> 1. **自检 / 判断标准**（"把喵去掉还像 AI 吗？"）—— 那是作者监工视角，要求模型站到自己输出外面审稿，就已经在演了
> 2. **场景分档表**（"闲聊当 A，干活当 B"）—— 有切换就有表演
> 3. **数量配额**（"一次一处""适度出现"）—— 这是**当场判不了的判据**，她开口前得先数一下自己做了几处，那道手续本身就是表演
>
> 取而代之是**存在式刻画**：写"她是什么样的"，不是"她该怎么做"。
> 检验一条规则该不该留：**把它删掉，句子意思变不变？不变就是装饰。**

对照我们的主卡：

| 我们的写法 | 属于哪一类 | 后果 |
|---|---|---|
| 「十条里顶多两条带梗」 | 数量配额 | 模型要先数数 → 干脆不用梗 |
| 「一次只挑一句说，别连念两句」 | 数量配额 | 同上 |
| 「❌别这样说 / ✅这样说」14 行 | 对照表 → 变成答案库 | 直接抄例句（实测已证实） |
| 「语气样例」27 条 | 答案库 | 复读的根源 |
| 「该收就收」判断标准 | 自检 | 模型在演"我在判断" |

**这就是「不够灵活」的机制性原因** —— 不是模型笨，是 prompt 把发挥空间用规则和例句填满了。

## 二、记忆系统：三个可选层次

### 层次 1：`LiveStream-Agent`（最值得抄的骨架，MIT）

`tian-xiu/LiveStream-Agent`，Python，抖音/B站弹幕 + edge-tts + SQLite。

**三级记忆实现（`agent/memory.py`，已读全码）：**

| 层级 | 载体 | 生命周期 | 实现 |
|---|---|---|---|
| 短期 | `deque(maxlen=20)` | 当前会话 | 滑窗，`to_text()` 拼成 `[时间] 昵称: 内容` |
| 工作 | SQLite `sessions` / `messages` | 当前场次 | 按 `session_id` 隔离，存 emotion/action/inner_thought |
| 长期 | SQLite `memories` | 跨会话 | `(user_id, key)` 唯一，`value` + `importance` + `access_count` |

长期记忆的写入是**键值对 UPSERT**：

```sql
INSERT INTO memories (user_id, key, value, importance, updated_at)
VALUES (?, ?, ?, ?, datetime('now'))
ON CONFLICT(user_id, key) DO UPDATE SET
  value = excluded.value, importance = excluded.importance,
  updated_at = datetime('now'), access_count = access_count + 1
```

读取 `ORDER BY importance DESC`，拼成 `年龄:22; 偏好:周杰伦` 塞进 system。

**优点**：50 行就能搬进 Node，不依赖向量库。
**缺点**：只能按 key 精确召回，没有语义检索；长期记忆的**自动抽取**在 `brain.py`（要另看），
`memory.py` 只提供 `remember()` 接口。

### 层次 2：`dsh-mnemon`（设计最完善，但搬不动）

`omdsh-dev/dsh-mnemon` —— 可组合记忆，三层：

| 类型 | 放什么 | 怎么进 prompt |
|---|---|---|
| Runtime memory | 偏好、约定、下一轮就要用的事实 | **每轮常驻**，压缩成 USER.md / MEMORY.md |
| Project Documents | 设计、调查、流程 | 先检索，相关才读 |
| Memory Spaces | 持久事实、决策、实体关系 | 按需召回，后端可换 9 家（Mem0 / Supermemory / Honcho / Hindsight…） |

**是 DSH 的进程内插件（JS），强绑宿主 SDK，不能直接用在 bridge.mjs 里。**
但「三层分工 + Provider 可换」的思路可以直接照搬。

### 层次 3：通用库（现在都不建议上）

| 方案 | 定位 | 我们的情况 |
|---|---|---|
| mem0 | 事实抽取 + 向量检索，最成熟 | 要额外服务/向量库，一条弹幕多一次 LLM 调用，**直播延迟受不了** |
| Letta (MemGPT) | 把记忆做进 Agent 运行时 | 要整套换运行时，等于重写 bridge |
| Zep / Graphiti | 双时态知识图谱 | 过重，观众量级用不到 |
| Memobase | 以用户为中心的**画像字段** | 思路最贴合，但仍是独立服务 |

**判断：我们体量（一个直播间、几百个观众）不需要向量检索。**
键值 + 分类 + importance 排序就够，等事实条目超过几千再考虑向量。

## 三、我们现在的记忆，到底差在哪

| 场景 | 现在的"记忆" | 实际内容 | 问题 |
|---|---|---|---|
| 直播弹幕 | `profileLine()`（reply.mjs） | 来过几次 / 送过几次礼 / 隔了几天 / 手打标签 | **纯计数，零内容** |
| 评论区 | `state/auto-reply-state.json` | `repliedComments`（已回 id）+ `dmSeen`（昵称） | **幂等账本，不是记忆** |
| 两边互通 | 无 | — | 直播认识的老粉，在评论区是陌生人 |

具体后果：

- 观众说「我在备考，好累」→ 下次来，她不记得。
- 观众点过三次周杰伦 → 不记得偏好，每次都要重新问。
- 评论区同一个人在不同视频下的评论，互不相干。
- 唯一长期记忆是**发生在我们自己身上**的（`recentSaid` 3 句），不是关于观众的。

## 四、建议方案（待确认）

### 记忆：M1 优先，一张表解决两个场景

新建 `cache/memory.db`（SQLite，Node 用 `node:sqlite` 或 `better-sqlite3`），一张表四个字段：

```
who        TEXT      -- 昵称（跨场景统一，抖音昵称）
kind       TEXT      -- fact / prefer / event / taboo
text       TEXT      -- 一句话事实：「在备考，明年考研」
weight     REAL      -- 重要度，人工/模型打分
touched_at INTEGER   -- 最后更新
```

- **写入**：直播每场结束、评论区每轮结束，各跑一次 LLM 批量抽取（一批 50 条，成本可忽略）。
- **读取**：每个弹幕按 `who` 查，取 `weight DESC` 前 5 条，贴 user 行（沿用 `profileLine` 的位置，**不进 system，不破前缀缓存**）。
- **跨场景**：直播和评论区读同一张表 —— 这是最大收益，也是现在最缺的。

### 人设：P1 改写法，不动护栏

1. 删「数量配额」类规则（十条两条、一次一句）→ 改成存在式描述「她梗用得少，抛了才接」。
2. 删「语气样例」27 条里的大部分 → 只留 6~8 条**下限**示例，并明说「别照抄原句」。
3. 对照表 14 行 → 只留硬红线（AI 身份、假送礼、坠机梗、金融），语气类全删。

预期效果：复读减少、临场反应变活；代价是需要试跑观察，红线部分不能一次删太猛。

### 性格：P2 让它们是三种人（可选）

参考 `dsh-persona-dafeiyu`：不是调浓度，是换人。
例如把「女仆」换成有明确职业和人生背景的第二人格（而不是"更温柔的大肥鱼"）。
**这一条要先定「她是谁」，再谈怎么写。**
