## 一、先补上上一轮漏掉的关键事实：直播伴侣是提权进程

```
直播伴侣.exe          manifest: requireAdministrator + uiAccess   ← High IL
直播伴侣 Launcher.exe manifest: requireAdministrator
```

这一条能解释之前所有「点不动」的现象：

| 现象 | 真实原因 |
| --- | --- |
| `SendInput` / `SetCursorPos` 没效果 | 跨完整性级别的输入被 **UIPI** 静默丢弃（`SetCursorPos` 返回 0 且 `GetLastError()` 也是 0，就是这个特征） |
| windows-mcp 的 `Click` 返回成功但光标不动 | 同上，它在 Medium IL |
| 沙盒外执行也一样 | 同上，跟沙盒无关 |

edrAgent（抖音安全组件）确实在，也确实拦输入注入，但**UIPI 这一层更靠前**。
上一轮把锅全推给 edr，判错了。

> 顺带纠正上一轮的一句话：「`Get-Process .Path` 读不到 ≠ 对方没提权」——
> 反过来才对，读不到**正是因为**对方 High IL 而我们 Medium。现在有 manifest 实证了。

还有一个实测佐证：从 Medium IL 读直播伴侣的 UIA 树，`nodeCount` 只有 **2**（光秃秃两个窗口壳，
一个子节点都没有）；提权代理读同一棵树是 **400+** 节点。

## 二、为什么 UIA 能过

`InvokePattern.Invoke()` 不是往输入队列塞事件，而是调用目标进程**自己注册的
UI Automation 提供者**，由它在内部派发「默认动作」。所以：

- 不过 `SendInput` / 输入队列 → 不被 UIPI 拦
- 不碰鼠标光标 → 不触发 edr 的输入 hook
- 不改任何文件 → 不触发 integrityCheck（上一轮打补丁就是死在这一步）

前提：**调用方也得是 High IL**，否则连树都读不到。这就是为什么需要一个提权代理。

## 三、架构

```
WorkBuddy ──stdio(MCP)──> tools/mate-mcp.mjs        Medium IL
                               │ HTTP 127.0.0.1:18085 + X-Mate-Token
                               ▼
                          tools/mate_agent.py       High IL（start-mate-agent.cmd 拉起）
                               │ UIAutomation
                               ▼
                          直播伴侣.exe              High IL
```

三层分开的理由：

1. **MCP 必须是 Medium** —— WorkBuddy 拉起来的子进程就是 Medium，改不了；
   但它只做协议转换，不碰 UI，所以无所谓。
2. **代理必须 High** —— 跨 IL 读不到 UIA 树，更别说 Invoke。
3. **token** —— 代理只听 127.0.0.1，但同机任何进程都能连 18085，
   加个 `.run/mate-token` 免得别的程序顺手把直播关了。

## 五、用法

1. 双击 `start-mate-agent.cmd`，UAC 点「是」。黑窗口保持开着（关掉就等于拔掉控制权）。
2. 之后直接说「开播」「关播」，或者调 `mate_status` 看状态。

代理没起来时 MCP 会明确说「去双击 start-mate-agent.cmd」，而不是给个含糊的报错。

单独调试（**必须在提权窗口里跑**，Medium IL 读不到树）：

```bash
.venv/Scripts/python.exe tools/mate_uia.py windows
.venv/Scripts/python.exe tools/mate_uia.py probe --out .tmp/uia.json
.venv/Scripts/python.exe tools/mate_uia.py state
.venv/Scripts/python.exe tools/mate_uia.py stop --dry     # 只看会点哪个，不真点
```

改完 `mate_uia.py` 不用重开 UAC：

```bash
curl -X POST -H "X-Mate-Token: $(cat .run/mate-token)" http://127.0.0.1:18085/reload
```

## 六、界面事实（实测，2026-10-29 / 13.2.3）

| 元素 | 真实名字 | 说明 |
| --- | --- | --- |
| 开播 | `开始直播` | 精确四个字，TextControl，有 invoke/legacy |
| 关播 | `00:02:28 关播` | **带直播时长前缀**，所以不能用精确匹配 |
| 关播确认 | `确认要结束当前直播吗？` + `取消` / `确认` | 点完关播必弹 |
| 在播旁证 | `实时码率: 2691kb/s`、`推流帧率:30` | 只有推流时才出现 |
| 结束提示 | `直播已结束` | 关播后的 toast，**不是按钮**，别被骗 |

判定规则（`state()`）：

```
has_stop  = 有节点名匹配 /\d{1,2}:\d{2}(?::\d{2})?\s*关播/
has_start = 有节点名精确等于「开始直播」
live      = has_stop ? True : (has_start ? False : (有码率旁证 ? True : 判断不了))
```

## 七、踩过的坑（都写进代码注释了）

1. **`auto.ProcessName` 在这个版本不存在**（1.x 才有）。改用 Win32
   `QueryFullProcessImageNameW`，跨 IL 也能拿到名字。踩之前表现为「窗口明明在，就是认不出来」。
2. **UIA 的根枚举会按完整性级别过滤**。`auto.GetRootControl().GetChildren()` 在
   Medium IL 下只有 15 个窗口，里面就是没有直播伴侣。改用 `EnumWindows` 全量枚举。
3. **COM 必须在处理请求的那个线程上初始化**。`ThreadingHTTPServer` 每个请求开新线程，
   `IUIAutomation` 是 STA 对象，跨线程用直接失败 —— 表现为
   「`list_windows` 有 17 个窗口，但 `ControlFromHandle` 全 None」。
   改成单线程 `HTTPServer` + `CoInitialize()` 一次。**这个坑排查了两轮。**
4. **同一颗按钮在两个窗口里各有一份**，坐标差一个窗口偏移（739px），
   只有一份是活的，另一份 Invoke 报 `E_ELEMENTNOTAVAILABLE`。
   所以 `act()` 必须**逐个试到成功为止**，不能只试第一个。
5. **关播按钮名带时长前缀**，`_score` 的精确匹配永远打不中。
   加了 `_bonus()`：命中时长正则 +400，「已结束/？/吗」−300。
6. **关播有二次确认**，只点关播不点确认 = 什么都没发生（第一次就卡在这，
   直播多跑了 1 分半）。现在 `act('stop')` 会自动找「确认」点掉。
7. **窗口最小化会丢掉整棵无障碍树**（400+ → 9 节点），这时读到的「没有关播按钮」是假的。
   `ensure_visible()` 在读之前把 `Chrome_WidgetWin_1` 主窗口 `SW_RESTORE` 回来。
8. **未开播时调关播必须安全失败**。界面上残留的「直播已结束」toast 名字里带「结束」，
   会被当成关播候选。现在有硬门槛：**没有「时长 + 关播」就拒绝执行**，宁可失败也不乱点。

## 九、风险与边界

- **只点「开播 / 关播 / 确认」三个按钮**，不碰登录、实名、推流码、账号设置。
  登录态和实名永远是主人自己的事。
- 开播前请确认画面来源、标题、封面都是对的 —— 这个工具只负责按按钮，不负责检查。
- 直播伴侣升级后 UI 改版 → 按钮名变了 → 会变成「找不到按钮」，不会乱点。
  这是有意的：**宁可失败，不可点错。**
- 代理是常驻提权进程。不用直播的时候把黑窗口关掉。
- 不改直播伴侣任何文件，不动 integrityCheck 校验的东西，升级不失效。
- `mate_uia.py` 里的按钮名/正则就是全部「知识」。哪天升级后失灵，跑一次
  `mate_probe` 拿到新名字，改两张表 + 一个正则即可。
